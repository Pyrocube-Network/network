# Performance

Run it yourself: `./gradlew :core:pump:perfTest`. The suite prints a markdown report and saves it to
`../../core/pump/build/perf/report.md`. The tests are tagged `perf`, excluded from `test`, never served
from the Gradle build cache, and only assert correctness (every chunk read is verified by its
checksum) and loose sanity floors: the numbers below are for reading, not enforcement.

## Setup of the numbers on this page

* 16 logical cores (8 physical with SMT), 32 GB RAM, NVMe SSD, Linux, JDK 25, default G1, 4 GiB heap.
* Dataset: 1 024 deterministic synthetic overworld chunks (24 sections: rolling hills, sea,
  stone/deepslate, caves, ore, gravel/andesite/diorite/granite pockets, grass, flowers, trees, sky
  light), 71.9 KiB of `PCHK` payload each. Generated by `SyntheticTerrain` in the test sources.
* Each measurement is the median of 3–5 timed runs after warm-up runs.

**Read the compression numbers with care.** Synthetic terrain is far more regular than a real
world: it compresses 9.6× with zstd-3, real worlds typically land well below that, and the stored
size per chunk (7.5 KiB) is therefore smaller than you will see. Throughput in MB/s of *uncompressed*
data also depends on how compressible the data is. Treat the absolute figures as relative indicators
between stages and configurations; run the suite against your own worlds for capacity planning (the
dataset generator is a few lines to replace).

## Results

### Single thread codec

| Stage | chunks/s | MB/s (uncompressed) |
|---|---:|---:|
| `PCHK` serialize | 11 716 | 866 |
| `PCHK` parse + validate | 23 753 | 1 755 |
| XXH64 | 207 846 | 15 354 |
| frame (zstd-3 + XXH64) | 8 217 | 607 |
| unframe (verify + zstd) | 19 414 | 1 434 |
| full chunk read from a frame | 10 956 | 809 |

Checksumming is not a cost worth thinking about (about 5 % of a read); compression dominates
writes, parsing and decompression dominate reads.

### Zstandard level

| Level | stored KiB / chunk | ratio | compress MB/s |
|---|---:|---:|---:|
| 1 | 7.7 | 9.4 | 682 |
| 3 (default) | 7.5 | 9.6 | 607 |
| 6 | 7.0 | 10.3 | 175 |
| 9 | 6.8 | 10.6 | 92 |
| 12 | 6.6 | 11.0 | 28 |

Going from level 3 to 6 buys 7 % size for 3.5× the CPU. The default is the right choice unless disk
is much scarcer than CPU; for archival conversions use `--level=9`.

### Multithreaded encode scaling

Serialize + compress + checksum of 512 chunks on a fixed pool.

| Threads | chunks/s | speed-up |
|---:|---:|---:|
| 1 | 4 706 | 1.00× |
| 2 | 9 278 | 1.97× |
| 4 | 17 733 | 3.77× |
| 8 | 25 646 | 5.45× |
| 16 | 25 709 | 5.46× |

Scaling is near-linear up to the physical core count and flat beyond it (SMT siblings share the
execution units zstd saturates).

### Region storage

| Operation | chunks/s | notes |
|---|---:|---|
| `writeAll`, strict | 17 577 | 2 regions, 2 commits, parallel compression |
| `writeAll`, deferred | 16 880 | barriers only at the end |
| `write` one by one, strict | 3 193 | 128 chunks, 2 flush barriers each |
| `read`, 1 thread | 10 351 | decode + verify |
| `readAll`, 16 tasks | 39 461 | parallel decode |

* Batching is worth 5.5× over per-chunk commits. On this machine the flush barriers themselves are
  cheap (strict vs deferred batches are equal within noise); on slower or shared disks they are not,
  which is the reason `PumpChunkLoader.saveChunks` commits once per region.
* `open + readAll` (opening a fresh `PumpStorage` per run) measured 11–58 k chunks/s between runs:
  it is dominated by creating native Zstd contexts and varies a lot, it says nothing about steady
  state and is not tracked.

### Concurrent readers on one storage

Each thread reads a stripe of the 1 024 chunks, eight passes, every chunk checksummed.

| Threads | chunks/s | speed-up |
|---:|---:|---:|
| 1 | 9 418 | 1.00× |
| 2 | 21 112 | 2.24× |
| 4 | 39 703 | 4.22× |
| 8 | 61 780 | 6.56× |
| 16 | 63 249 | 6.72× |

Reads are optimistic and lock free (see [ARCHITECTURE.md](ARCHITECTURE.md#concurrency-design)); the
super-linear start is JIT and cache warm-up favouring the multi-thread configurations in a short
benchmark, the useful reading is that throughput keeps rising to the core count.

Mixed workload, 3 s: 15 reader threads sustained **55 271 reads/s** while a writer committed
**2 894 chunks/s** in batches of 32 with strict durability, every read verified: readers are not
blocked by commits or flush barriers.

### PUMP vs Anvil (256 chunks, one region)

| | PUMP | Anvil (zlib) |
|---|---:|---:|
| file size, sector padded (KiB) | 1 961 | 2 480 |
| compressed chunk bytes, no padding (KiB) | 1 921 | 1 893 |
| write, 1 thread (ms) | 54.5 | 191.1 |
| write, 16 threads (ms) | 12.0 | n/a |
| read and decode to the chunk model (ms) | 23.7 | 77.1 |

* **Size is a wash on equal footing.** Unpadded, PUMP data is 101 % of Anvil's: zstd-3 over a
  byte-indexed palette layout lands where zlib over bit-packed palettes does. The 21 % smaller file
  comes from 256 byte sectors against Anvil's 4 KiB, which matters more the smaller your chunks
  compress (sparse void/skyblock chunks benefit most, dense terrain least).
* The speed difference is real but partly a property of the pipeline, not only the format: PUMP
  writes need no per-block name lookup or NBT tree, and reading needs no string parsing. Both
  single-thread rows run the whole path on one thread.
* "Anvil write" includes building the NBT tree via the transcoder, which any server saving Anvil
  has to do too; Anvil reading includes block-name resolution and unpacking, as a loader must.

### Minestom bridge

| Stage | chunks/s | notes |
|---|---:|---|
| `Chunk` → `PumpChunk` (snapshot) | 60 789 | the only part under the chunk's write lock |
| `saveChunks` end to end | 96 856 | 256 chunks, strict durability, one region, parallel |
| `PumpChunk` → `Chunk` (populate) | 14 380 | palette fill, light, heightmaps, block entities |
| `loadChunk` end to end | 20 288 | read + decode + populate, one thread |

The chunks in this test are the simple generator output of a Minestom instance (mostly uniform
sections), so the snapshot cost is optimistic; populate is the most expensive step of a load
because `Palette.setAll` visits every block of non-uniform sections.

## Tuning

| Goal | Knob |
|---|---|
| fastest saves | save in batches (`saveChunksToStorage`, `PumpStorage.writeAll`), never loop over `write` |
| smaller files | `withCompressionLevel(6..9)`; saves get slower, loads do not |
| more throughput on big machines | `withParallelism(n)` (default: all cores), keep ≤ physical cores for CPU bound bulk work |
| many regions touched at once | `withMaxOpenRegions` (default 64); the LRU never closes a region in use |
| bulk conversion | the converter already uses deferred durability; use `--threads` |
| latency of the save path | the chunk write lock is held only for the snapshot; compression and I/O are outside it |

## Methodology notes and pitfalls found

* A first version of the concurrent reader benchmark timed ~1 000 reads per run (about 15 ms) and
  showed throughput *collapsing* at 16 threads. It was an artefact of task hand-off dominating such
  short runs, not of the storage: with long-running per-thread stripes (current benchmark) and in the
  mixed workload, 16 threads scale as shown. If you write your own benchmark, give each thread
  enough work.
* The first PUMP-vs-Anvil comparison produced a flattering "45 % of Anvil's size" on over-regular
  data because of the 4 KiB sector padding; the report now shows padded and unpadded sizes
  separately.
* Numbers vary ±10 % between runs on a desktop machine (turbo, background load). Compare ratios
  within one report, not across reports.
